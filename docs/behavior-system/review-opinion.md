# 对现有行为方案的审查意见

2026-10-19。审查对象为本目录原有五份文档。结合此前讨论，由另一个独立对话审阅，再对其结论和我的判断进行反向质询。本文只记录最终意见，不替换方案；原文未改。

## 我的结论

**保留现有结构。它已经实质纠正了上一轮“普通行为也要承担一整套生命周期协议”的问题，没有发现需要重建架构的依据。**

这个判断有范围：已展示的普通行为和模板复用有实际依据；不能进一步宣称所有复杂行为都便宜、执行基础已经验证，或者整份行为目录都能只改参数实现。当前仍是设计，未做运行验证。

确定需要统一的是两组动作语义冲突。其他值得验证的例子，不应被升级为推进整个方案的前置要求。

## 这次修改解决了什么

上一轮的主要问题不是漏了几个极端情况，而是不断用状态安全问题扩大结构：跨轮申请批准、版本、许可、通用恢复，以及要求所有行为写到购买案例的精度。普通内容作者因此需要理解、填写并维护大量与行为本身无关的规则。

现稿减少的是真实重复工作，而不只是字段数量：

| 内容 | 作者现在承担什么 | 不再逐项承担什么 |
|---|---|---|
| 复用已有动作的普通行为 | 一行行为、分数，必要时加条件或显示名 | 执行寿命、取消回调、恢复策略、结果生产协议 |
| 新的简单动作语义 | 另声明一次 once／hold、身体与工具要求，必要的效果 | 为引用它的每个行为重写执行器 |
| 手机换成书 | 工具与动作参数；动作语义尚无定义时补一次 | 另写取出、使用、中断和后续腾手流程 |
| 公告栏换成饮水处 | 设施目标与动作参数 | 另写接近、占位、到达和释放预留 |
| 一类买卖服务 | 商品与所需准备等内容规则 | 每个顾客复制队列、结账、交付和防重复检查 |

依据：[主方案 §1–3](execution-plan.md)，尤其第 28–30、39–69、90–135 行。

例如：看手机结束，手机仍在手；随后整理衣服赢得选择，所需手不空，就先由共用准备收起手机；实际持物变化成立后再整理衣服，once 结束后进入共享冷却。整理衣服这一行不需要知道此前是看手机、读书还是拿别的东西。这才是修改一项不牵动其他行为的具体收益。

这仍需要开发共享执行器、实际身体／物件状态、资源裁决和模板。**把成本集中起来，不等于这些基础能力实现起来很小。**现稿第 69、270 行已承认这项成本，不能反过来说它在冒充现有工程已经支持。

明确停用项可以缺字段、已定义语义可以缺素材，二者都不阻挡其余内容；已启用的错误声明仍报错。这也解决了“为了继续做一小部分，先被迫补完整个目录”的问题。

## 两处确定的语义冲突

### 台面取物与地面捡物混用

[主方案](execution-plan.md)第 64 行把 `pick_up` 定义为从可及支撑面拿取，第 226、241 行又让摊主用它取回台面上的货。

[动作清单](actions.md)第 184、310 行明确区分：地面用 `pick_up`，台面用 `take_item`。[行为盘点](behaviors.md)第 212 行也要求摊主先 `take_item`。

具体分歧是：已结账 → 顾客被电话打断 → 货放到摊位台面 → 顾客回来领取。同一个环节，主方案和动作接口要求不同动作。文字阶段也应统一语义，否则以后条件检查和素材绑定会分叉。

**建议统一为台面取回用 `take_item`，保留 `pick_up` 的地面含义。**只需统一接口，不需要新模板。

### 座位起身的范围被扩大

主方案第 65 行让 `stand_up` 处理“坐着／蹲着”；动作清单第 72–73 行却把它限定为座位起身，并另列地面起身 `get_up_ground`。

这不是缺素材的问题，而是同一个动作名有两套范围。共用准备读取实际支撑后，必须选择符合该支撑的已定义动作。

**建议统一 `stand_up` 的范围，不能用它默默覆盖所有起身。**只启用座位起身完全可以；其他起身能力尚未定义就保持不可用，不要求这轮补全。

## 我质询后不再当作缺陷的意见

- **“握手配对成功后必然掉分散伙”不成立。**这是我先假定匹配成功就清除邀请，再推出的后果。原文没有规定这一步；不能把自己的假设当作方案错误。邀请处境覆盖到哪个阶段，可在实现计分时核对，不需要为此另建接受协议。
- **“电话没有完整生命周期，所以当前方案不能成立”不成立。**保留连接与停止身体动作分开，是此前要求保留的语义；没有理由要求先完成电话系统，才能做其他已定义行为。
- **“没有坐姿进入规则”说得过强。**主方案允许必要身体准备，行为盘点第 184–185 行已写清到位、坐下、坐姿保持，以及已坐时跳过重复坐下。实现者据此把坐下放进共享准备是合理的，不需要因为主文概述没有重复展开，就再要求一套过渡系统。
- **“direct 无法表达单向招呼”没有依据。**direct 的 self 是可覆盖的默认；候选已有实际目标；行为盘点明确朝对方挥手且不要求对方回应。最终字段尚未定名，不等于必须加一个模板才能做。
- **“被替换不加冷却必然来回切换”没有得到反例支持。**有效分不变时，挑战者必须严格超过当前分及其非负保留扰动，不能凭同一组固定分数循环替换。执行改变了处境之后可能重新选择，不自动构成机制错误。

这些撤回不表示对应实现已经验证，只表示它们不能支撑要求方案扩张的结论。

## 还有什么值得验证，但不必挡住其他内容

比继续加深购买边界更有价值的，是检查不同内容是否真的复用同一套能力。以下是可选的验证例，不是要求现在全部补完。

### 一条单向招呼

发现 B、C → 分别形成指向两人的招呼候选 → 按距离等因素选择 B → 必要时腾手 → 朝绑定的 B 挥手 → once 完成，对这次行为与目标冷却；B 始终可以继续原事。

这能检验普通目标型行为的新增工作量，避免只用三个 self 样例证明所有普通内容都便宜。候选、目标、准备、执行和冷却都有现成设计依据，不应为这个例子另造系统。

### 一次坐下后改看书

接近座位 → 尚未坐着时坐下并建立实际支撑 → 保持正坐 → 改看书后仍占原座位 → 需要站姿的事情赢得选择时再起身。

这检验共享准备、实际支撑与当前事情是否真的分离。它不要求规定所有姿势转换，也不证明动画已经自然。

### 两种商品共用一次服务结构

现文已给出：买方选择商品，卖方读取；买方准备工具、卖方准备商品可以并行；双方条件成立后共同确认结账；交付效果与本次成功一起提交。结果的有效性和本次服务绑定也已有共用约定，不能说全文只剩动作字符串。

称重水果需要商品准备；直接交付的成品省去称重。按现文，这个差异可以留在商品／过程配置，不需要改队列、结账和交付模板。

尚未展示的是一种具体服务的完整填写量：选择哪件商品、用什么支付工具、什么算准备和条款成立。用一个小例子可以核算成本；目前缺这个例子，**只意味着复杂内容的具体填写成本尚未充分展示，不意味着必须设计新机制或先定最终 JSON 语法。**

持续同行、棋局回合、共同身体支撑另有不同语义。现稿没有证明这些都能套一次握手或购买模板，也没有必要作这种承诺。明确需要的新过程或能力，应按实际内容增加。

## 需要保留的取舍

默认不保存所有被替换的未完成目的。买水果途中若高层真的改成看手机，之后不会保证自动续买；若只是购买内部允许的消遣，购买仍是当前事情。队列、已付未取、实际持物和支撑按自身规则保留。这是一项明确简化，不应再偷偷补回通用待办恢复系统。

同帧裁决也不是求全局最优：已有有效预留受保护，失败者只试一次后备，释放出的闲置预留本轮不反复回填。因此可能暂时少用一个位置，换来稳定且有界的处理。文档已经说明这一取舍，不能仅凭利用率不最大就要求重建分配器。

我的建议是保留这些边界。原文如需后续修订，先统一已证实的动作语义冲突；其余例子用来检查实际复用和表现，不再把每个可想象的情况变成所有行为作者必须填写的规则。

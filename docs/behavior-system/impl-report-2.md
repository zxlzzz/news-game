## 共用能力与数据

### 共同一次

`make_joint → requests → system._grant → start_joint → advance_joints → commit_joint` 是三处共同使用的唯一路径。

共同请求捕获双方当前事情的实例 ID、动作、使用点、商品及服务实例。位置、人物角色、物件资源整组请求，按双方有效分的最小值进入第一批同一个分配入口。握手布置连两人的准备资源一起申请；任一资源失败，不先扣住另一半。动态双人使用点与普通设施即使 ID 不同，只要位置重叠，也会在同一入口冲突。

先只读预览并裁决，再提交所有最终选择；最后才核对双方选择仍相容、实际站位／朝向／支撑／持物成立，启动两人的动作实例。等待身体可换成 hold，配合意图仍在当前事情里，不依赖对方“已经播起来”。同一共同实例累计一次进度，完成时重新核对实例与实际条件，再同步提交效果。取消后保存的旧引用不能重写效果。

三种效果仅有提交的业务差别：握手结束双方本次目的；结账在摊位写 `paid[buyer] = item`；交付同一步把货从摊主移到买家手、删 paid、记录本次成功。没有三套同步、计时、取消或双方就绪代码。

`work()` 调用第一批的 `action_preview()`，因此起身、腾手、取工具没有复制。`waiting()` 先用目标动作的条件产生同一套准备，最后才换为 `pair_wait` hold，并保留该目标动作的继续条件；不会把整段 give/receive/confirm 的 once 挂成无限等待。

### pair_once

行为行引用 `pairs.handshake`，这项语义声明集中填写 offer、reply、wait 和布局引用。所有人物目标都由模板枚举。`invited` 是模板提供的处境，进入原来的 base 表，仍与对方当前事情比较。双方同时发起按最早发起者分 offer；同刻用稳定 ID，不靠人物数组顺序。

### service_customer / service_vendor

两条行引用 `services.fruit`：选择／称重动作、支付工具、两个摊主消遣动作、共同结账与递接动作、包装 TODO 和递接布局引用。设施配置提供位置、排队半径、台面及有限商品；商品只配置实际 item ID、是否称重、是否包装。

设施实例的 `queue_ids` 保存等待名次，`paid` 保存已付未取。它们不在人的当前事情里。`active` 只保存本次服务的买家、商品和当前已完成的局部结果，服务取消即删除，不当恢复任务。`keeper/open` 是设施职责与营业事实，不由身体请求统一清空。`withdraw()` 明确撤回名次，`end_duty()` 明确结束摊主职责。

买家和摊主分别按事实选工作，不共用全局步骤号。选择完成后买家立即用实际钱包准备付款，摊主按商品独立称重。必要工作随事实变化替换旧身体请求；吆喝不锁住接待。

## §6 逐项落实

| 说法 | 实现与验证 |
|---|---|
| 相容意愿是双方当轮互选，不另加“接受”候选 | 读两人的当前 pair 绑定；错轮互邀检查中 A 先 hold，下一轮 B 因 invited 选 A，建立一份互动 |
| 同时发起只建一个实例 | 稳定的人物二元键去重；两人同时邀 C，只允许 C 当前选择的那一对；倒转人物数组结果一致 |
| 单方等待、invite_wait、again | `handshake_wait` 明确 hold、站姿空手、clip 空；下框“等对方回应”。8 秒无人选择即结束失败尝试，按共享 again 冷却该绑定；检查覆盖 |
| 先做不依赖伙伴的准备，再共同布置、就位 | 单方等待就可复用起身／腾手；互选后整组申请双方使用点和准备资源，再各自走到位。站位直接读取 handshake_offer.partner，不复制几何进表 |
| 真正共同执行角色 | 发起方 handshake_offer、回应方 handshake_reply；检查确认两动作都启动、实际间距符合现有布局 |
| 换事情／离开／条件失效结束互动 | maintain 核对意愿；共同执行还核对身体实例和条件。实际改选手机后另一方也结束；保存的旧共同回调无法提交。已发生持物不回滚 |
| 不假称扶人能力 | 未启用扶人、没有添加共同身体支撑执行能力 |

| 共同结账 | 选择及商品准备完成、钱包实际在手、双方就位且仍是该次服务，才共同 present_payment_tool/confirm_checkout；结束点同步写 paid。三个支付语义 clip 均为空，不绑定 pay 或 wallet_takeout |
| 货在台面／手里 | 台面 take_item 是真正的 once 效果：检查可及、空手、物件仍在指定台面，再从台面移到手。摊主中途腾手用原 put_down，指定本摊台面；不在取消时瞬移货物 |

## §8 事实、中断与区分检查

| 区分项 | 实现、验证或边界 |
|---|---|
| 排队时改做看手机 | 确定性检查：仍在区域，名次保留；摊主轮到他时，购买已非当前事情，则跳过、删名次。离区、明确 withdraw 也删除；队列不强夺手机事情的身体 |
| 已付未取 | 按本摊／买家保留，跨中断、其他顾客和长时间；交付／买家不存在时删除，均有检查 |
| 电话连接 | 本轮只启用看手机，没有开发通话活动或虚构“已保持电话连接”的验收。执行器不按停止身体请求清理额外活动；真正电话连接仍需后续通话模板实现 |
| 摊主职责与营业 | 设施维护，当前身体／事情停止但人仍在摊位时不清除；离摊清 keeper，end_duty 明确结束职责。检查覆盖短暂停止仍保留、实际离摊清除 |
| 座位、服务点占用与预留 | 延续第一批真实占用与预留分离。新双人布局也与普通点按位置查冲突；身体没有实际离开前继续阻挡。第一批座位／公告点检查仍通过；本批验证买家实际离开服务位 |
| 持物与已提交效果 | 取消不清持物，不把尚未完成的 put/take 当成成功；原有各准备阶段的取消检查仍通过。购买前后检查世界中每件物品位置唯一 |
| 两人争椅与一次后备 | 第一批确定性检查原样继续运行；共同布局复用同一分配器。本批新增共同布局与高分普通设施争同点，验证失败时不会先占另一伙伴位置，倒序同结果 |
| 错轮互邀、真正改做手机 | 本批 handshakes 检查覆盖；等待请求未消除意图，手机选择真正取消互动 |

| 拿取、交付后旧回调与转赠 | 原来取物准备旧实例检查保留；本批保存握手／结账旧共同实例，取消后提交失败，交付成功后旧共同回调再次提交也失败；立即转赠仍有成功结果 |

## 新增成本核验

检查实际删除并只恢复 handshake 行，验证其余表内容与之前完全相同、声明合法，并运行真正的互邀、准备、就位、共同执行。没有为握手新增专用执行分支，pair_once 也不识别行为名 `handshake`。

严格说，首次接入一种 pair 不能只算“行为一行＋三个普通动作声明”：还需要一份 `pairs.handshake` 的角色／布局声明，告诉模板谁等、谁 offer、谁 reply、引用哪个素材布置。这是方案 §6 要求的语义信息，不能从动作名可靠推导。本批将这项成本明确计入，不说已经做到字面上的“只有一行加普通动作声明”。在这份共用 pair 声明已存在时，新增／重新启用握手确实只改一行；首次新增另一种双人语义还要提供其动作与角色布局声明，不改引擎。

## 素材需求与最简单解释

新增需求已集中登记在 actions.md：单方邀握 hold、等待配合的空手／钱包／商品持握姿态、钱包取出保持与支付准备、展示／确认结账、台面 take_item、包装片段及流程、跨摊位递接的接触适配。

没有扩展方案补洞，以下按最简单解释处理：

1. market_stall 的顾客标记相对摊主为正前方 1.16 米；give_item.partner 是横向 -0.28、前方 0.94 米，两者不是同一布置。选择／结账用原 customer，递接前移到素材声明的 delivery 点。称重另去 fruitweigh。只是文本设施引用，不假称两种模型合成后柜台几何已验证；现有 give/receive 交接帧也还没有证明同步。
2. 称重文字表示将所选台面货物在称重区处理完，处理后仍在本摊台面，不伪造一只一直拿货的手；交付准备才 take_item。若取消发生在交付前已经拿起货之后，下一项需要手的看摊工作就先 put_down。该路径已用纸上时序检查强制跑过。
3. prepare_payment_tool 是“钱包在手并保持可用”的语义，实际取物只由 take_tool 提交，没有第二个就绪标记或重复取钱包片段。双手分别持物仍沿用第一批单一手持物槽；素材需要用手的动作按实际空手或持指定物声明，未引入左右手规划系统。
4. 当前没有价格、找零、退款、完整库存经营或包装流程。条款只取本次实际选定商品和其准备要求；需要包装明确结束 TODO，不临时发明包装成功。
5. 排队区是一个允许多人的区域与一个接近点，不实现队列中的精确几何间距或人群避让；名次与服务独占点是分开的。商品选择只在可买的实际库存中抽一个，不引入个人商品偏好。人物 ID 用于同刻稳定排序，不靠数组先后。
6. 文字执行以共享演示时间提交共同语义，不读取素材交接帧；站点朝向可在等待／工作时设定，不宣称连续转身和动画衔接已经制作。后续接真实播放时，替换共同进度／提交反馈入口即可，不必重写队列、paid 或三处同步逻辑。

## 返修

2026-10-20，按审阅意见只调整以下四处；已接受的共同一次、支付准备、paid／队列事实和中断流程保持原有语义。

1. **摊位位置由动作和场景配置决定。** `service_actions/service_posts` 从服务实际引用的 choose、可选 weigh、idle、checkout、delivery 动作声明收集 post，不再固定加载两种类型或列举 vendor/customer/fruitweigh。摊位配置新增 `posts` 映射，例如 `{"customer":"res://types/market_stall.tscn", "vendor":"res://types/market_stall.tscn", "fruitweigh":"res://types/fruit_stand.tscn"}`；代码只到对应类型查找 `post_<kind>`。运行中的顾客／摊主职责仍是模板的语义角色，它们的站点从 choose／idle 动作推导；称重位置也从称重动作推导。没有引用 weigh 的服务不需要称重动作和称重位置，商品若要求未声明的称重则启动报错。缺提供者、类型缺标记等声明错误返回启动错误，不写入半套位置。demo 只补原水果摊的提供者映射。
2. **统一伙伴布置和摊位旋转。** `partner_pose(clip, pos, yaw)` 读取 clip-setup.partner，用发起人的朝向旋转相对位置，并将相对 yaw 加到发起人 yaw；握手与交付都调用它。摊位配置新增 `yaw`，单位度、默认 0。类型标记位置绕 origin 旋转，朝向加摊位 yaw；排队／出口位置也绕同一 origin 旋转（配置坐标保持原来的零旋转世界坐标写法）。台面仍由场景独立配置实际位置。交付布置基于旋转后的实际摊主标记，不再假设摊主朝向为 0。
3. **处境声明只有一份。** `TEMPLATES` 按模板登记其处境名与求值函数。声明验证的 `has_condition()` 和 system.gd 的 base 计分都查这份登记；system.gd 不再列 invited/paid/calling 名单。原有分数、事实来源与最高命中规则保持不变。

在容器里用 Godot 4.7.2 软件渲染实际跑了测试场景（截图并逐帧导出各人状态），发现并修正：

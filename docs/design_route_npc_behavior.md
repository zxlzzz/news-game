> **status: finalized** — 部分实现（2026-09-27）

> 实现（`godot/npc/behaviour.gd`，由 `npc/crowd.gd` 驱动，场景在 `population.tres` 里打开 `behaviour`）：一张全局表 `npc/behaviour-table.json`，人的标签系数 `npc/behaviour-people.json`（现在只有一种人）。已做：候选来源"自身"（逛、离开、原地小动作）和"物件"（各类型里的 `post_<种类>` 位置：长椅、公交站、摊位、棋桌）；距离衰减、抖动只用来挑挑战者、和当前比一次；资格条件 `taken:<种类>`（摊主在才有顾客、有人下棋才有人围观）。**没做**："周围的人"这一类来源、双人请求、活动记账里的吆喝抬分。实现时补了一条规则：一行做完后，同一个人 `again` 秒内不再挑它（不是当前分数随时间下降；没有它，人刚从长椅站起，长椅仍是身边最高分，马上又坐回去）。另一处落实：抖动只在人没事做、挑新行为时加，挑中的行为带着这份抖动当自己的分数；进行中别的候选不加抖动，要比它高才换（每次重想都重抽抖动会让分数相近的来回换；比较时丢掉抖动又会让刚挑的远处目标半秒后就被换掉）。统计检查 `godot/tools/check_behaviour.gd`（打印每 10 秒各行为人数、各行为开始次数、半路放弃的去向；有行的位置种类都要有人用过，场景里有、表里没行的种类只打印）。动作要什么（位置、配件、另一人）记在 `npc/clip-setup.json`，见 §5.1。

# NPC 行为系统 — 设计路线

> 素材接口说明（2026-09-20）：本文的“动作 json”表示待播放的动作片段，不规定最终存储格式。当前素材是源 NPZ + meta.json，绘制时按 [NPC 映射规格](design-plans/npc-skeleton-mapping.md) 映射；不要求另存映射后的坐标。行为选择规则与位置接续约定不变。

2026-09-15 讨论结论。本文只描述系统本身，不含实现细节；实现情况见开头。

---

## 0. 这个系统解决的问题

**什么时候换下一个动作 json，换成哪个。**

只有这一件事。NPC 想什么、为什么这么想、社会关系、情绪建模，都不在这个系统里。

动作外观的最小单元是一个动作 json。系统只决定播哪个，不管里面装什么（整段动作还是关键帧，归美术供给）。

---

## 1. 运行时

一个 NPC 同一时刻播一个 json。

候选行为由**外部**产生，产生方三类：

- **物件** — 场上的设施：长椅、垃圾桶、摊位、棋桌、门
- **周围的人** — 视野内的其他 NPC
- **自身** — 这个 NPC 自己

三类吐出的是同一种东西：

```
{ 播哪个 json, 一个数, 指向谁或哪里 }
```

系统做一件事：把所有候选**排一次序**，和「当前正在播的那个」比一次。高就换。

**比较只发生在这一处。**没有子系统，没有仲裁层，没有中间层。

不保证任何行为播完。被换走是正常结果，不是要修的问题。

### 为什么不分系统

分系统的形式是：对物 / 对人 / 对自己各自先决出一个赢家，中间层再从三个赢家里挑。

这会坏：中间层拿到三个赢家时，依据已经在子系统内部被丢掉了，它凭什么说对人那个比对自己那个更该做？只剩两条路——回去重新拿原始信息（第一次决策白做），或者给每个子系统配权重（拍脑袋，且以后加一个行为可能要回去调权重，撞「改旧东西不牵动全身」）。

**两次决策比一次决策拿到的信息更少。**这是分系统的固有代价，实现得好也绕不开。

注：对物 / 对人 / 对自己这个划分本身是成立的，但它落在**产生候选**那一侧（候选从哪来、怎么被发现，三者确实不同），不落在**比较**那一侧。

---

## 2. 那个数怎么来

### 一张全局的表

一行 = `什么处境下 · 播哪个 json · 基数`

**行数不等于动作数。**同一个 json 可以出现在多行里，值不一样：同一个「停下看」，有人吵架时是 8，有人摆摊时是 3。

不进表的东西（这些是正交轴，自动组合）：姿势基座（站/坐/蹲/走/靠/躺）、情绪修饰、人型变异（老人走 vs 年轻人走）。

填出来的手感（六行样例）：

| 谁吐的 | 什么时候吐 | 播哪个 json | 数 |
|---|---|---|---|
| 自身 | 手上空着、没别的事 | 刷手机（走） | 2 |
| 垃圾桶 | 这人手上有垃圾 | 扔垃圾 | 6 |
| 长椅 | 有空位 | 坐长椅 | 3 |
| 吵架现场 | 在视野内 | 围观站 | 7 |
| 对面那人 | 他朝我走过来并停下 | 点头打招呼 | 6 |
| 摊位 | 这人是摊主、站在摊后 | 吆喝 | 4 |

量级凭感觉：底噪 1-3，冲着某个东西去 4-6，出事了 7-9。填错一行只影响那一行，不传染。

### 标签系数

NPC 身上不带自己的表，只带标签系数。全场共用同一张表。

`seller: 0` 的路人永远不会挑到摊主动作；`seller: 0.3` 是兼职卖菜的大妈。**人不分类，只是系数不同。**

- 标签一律当**乘数**用。0 自然等于这行不参加比较，不另设资格规则。
- 一行挂多个标签时，系数**相乘**。任何一个是 0，整行灭掉。
- 标签跟美术侧横切要用的词（需要场景锚点 / 双人 / 仅老人）大概率是同一批，两边共用一套，不维护两份。

### 距离与抖动

- **距离衰减**：全局一个公式，所有行共用。不是每行一个参数。
- **抖动**：加在「挑」那一步，不加在来源里。全局一个旋钮，调一次能看出整条街是变呆板还是变神经质。

（The Sims 的做法也是在高分的几个里随机取一个，不是每个物件自己随机。）

### 不做「当前行为的分随时间下降」

曾考虑让当前行为的数随时间衰减来促成切换。**否掉了。**

反例：两个候选都是 10，当前行为开始是 12、每秒降 1，两个动作各要 5 秒 —— 每次刚过 2 秒就被对面抢走，两个动作永远播不完，一直重启。

更根本的理由：在做事情的时候引入时间变量本身就不靠谱。时间过去不等于事情做完了。而「几秒后它落到 8 被换走」要么是参数填错了（改那一行），要么是它真的不重要了（被换走本来就可以接受）。

---

## 3. 两个人的事

判据：**这个动作的画面需不需要另一个人的身体。**

### 需要 → A 挑的是一个请求，不是 json

握手、击掌、搀扶、拥抱、背人。A 单方面播不出握手，所以 A 挑中的只能是请求。

B 那边照常比一次，不接 A 就收回。画面上是伸手没人握 —— 读得出所以然，是街上真会发生的事，不是 bug。

约不成本来就比约成多。频率是参数，调出来看。

### 有物件可以记账 → 活动记在物件上

摊位、棋桌、售货机、门。

**不做成请求**，因为请求有方向，而两个方向都会发生：摊主吆喝招来顾客，或者顾客自己感兴趣走上来。做成请求就得实现两遍。

物件记着谁在跟它打交道：

- **摊主先**：摊主在摊后没事干 → 摊位吐「吆喝」→ 吆喝这个动作把摊位对周围人的数抬高 → 路人本来对摊位是 2，变成 5，有人拐过来
- **顾客先**：没人吆喝，摊位对某个人的数本来就高 → 他走过来 → 摊位记上有客 → 摊主收到「接待」的候选

两条路的画面和顺序不一样，**两种情况都在**。两边齐了之后，摊位才放出只属于这个活动的候选：指选、递货、找零、悔棋、托腮。这一段两种情况走同一条路 —— 不管谁开的头，交易做起来就是那个样子。

### 活动开着才放出的候选

踮脚看 / 伸脖子看 / 交头接耳，只在「已经在围观」时成立；找零 / 接东西，只在交易进行中成立；点头 / 摊手 / 一只手指点，只在交谈中成立。

这些行照样在表里，但带一个**资格条件**：相应活动开着才进入比较。加在产生候选那一侧，比较仍然只有一处。

（这就是 Ready or Not 后来补的 Gates：分数合理不等于这个动作该发生。）

好处是「踮脚看」和「伸脖子看」之间仍然是一次真比较 —— 前面挡得死就踮脚，挡得松就伸脖子。这是「看得出所以然」。

### 什么时候可以把几个动作放一行随机取

卡尺：**观众能不能读出来为什么是这个而不是那个。**

- 挠头 / 揉眼 / 拍灰 —— 读不出差别，放一行随机取，白赚变化
- 踮脚看 / 伸脖子看 —— 差别是有原因的，拆开是「看得出所以然」，合并就丢了

这不是省行数的手段，是判断哪些行本来就不该分开。

---

## 4. 系统要记的状态

只有两样：

1. 这个 NPC 当前在播哪个 json
2. 物件上 / 两个人之间开着什么活动

## 5. 和素材播放的接口

**位置接续由播放端负责，不要求素材首尾固定成同一个姿势或世界坐标。**

切换可发生在任意帧。下一条片段从 NPC 当前所在的位置接着播，片段内根节点的相对位移接续到场景位置，不能把素材的绝对坐标直接当作 NPC 的世界坐标。移动片段同样遵守此约定；根位移与导航的速度、方向、避障如何协调归播放/移动实现，不能重复累加两套位移。

首尾姿势对齐只改善完整播放时的衔接，不能解决中途切换。当前设计允许直接换动作，不要求先播退出段；蹲姿切到行走等姿势跳变，等实际画面不能接受时再补过渡。

动作如何使用由行为侧决定，不强制素材按一次性、持续状态、移动分类。首尾约束和进入/保持/退出分段均为可选加工；需要分段时可在一条素材上记录位置，不必分别生成三个文件。现有素材不因缺少统一首尾姿势而作废或批量重出。

### 5.1 动作的布置（`godot/npc/clip-setup.json`，2026-09-27）

原则：每样位置信息只写一处，写在不动的那一方身上；动作的声明只写名字，不写几何。

- 一条动作最多声明三样，单人、不碰物件、不拿配件的动作不写：
  - `post`：要哪种位置。人在物件上的站位只在物件类型 `.tscn` 的 `post_<种类>` 标记上（位置 = 人的根，+Z = 人面朝的方向）。
  - `item`：拿什么配件（`types/held_<名>.tscn`）、用哪只手（`left`、`right`、`both` = 两手中点、`back` = 颈根）。配件在手里的偏移是那个类型里 `model` 节点的位置，初值为零（模型原点就是握点）。推着走的购物车、婴儿车不算配件：是普通物件（类型分组 `pushed`），有 `post_push` 标记，跟着人的根位置走。
  - `partner`：两人动作。做这个动作的人在自己身上开一个位置（`at` = [x, z]、`yaw`，相对他自己），另一人用 `clip` 站上去，两人同步播。现在只有 `give_item` → `receive_item`。
- 行为表的 `from` 不变。检查：声明了位置种类的动作只能出现在同种类的 `post:<种类>` 行里（`crowd-params.json` 的 `posts` 同样），违反就报错退出。
- **缺东西是唯一的例外**：声明引用的位置没有任何物件类型提供、配件类型不存在、另一人的动作文件不存在时，不退出：游戏里这条动作不进候选（一行的动作都缺东西时，这一行就没有候选，和"没物件提供这种位置"一样），空地里这条灰掉并写明缺什么。其余数据错误照旧报错退出。
- 手要碰的点（原 `support.json` 的 targets）存成物件类型上的 `touch_<动作>_<关节>` 标记，现在只存不用，等以后做 IK。
- 调这些相对位置用空地场景（`godot/scenes/empty_ground/`，`godot/README.md`"空地"一节）：拖人、拖配件、拖另一人，松手写回上面三处之一。

### 5.2 动作转换（未做）

打分表只回答"换不换、换成哪个"，不管"从这个动作能不能直接接到那个"。还需要一张图：**哪个动作后面能接哪个**。例：

- walk → idle → eat / sit / walk
- walk → sit → walk
- walk → run → walk，或 run 中摔倒（fall in run）
- walk → 走路中摔倒（fall in walk）→ walk

约定：

- 切换照旧允许直接换（§5），这张图不要求过渡段；它只限定哪些接法允许出现在候选里。
- 怎么表示未定：是单独一张边表（动作 → 可接的动作），还是写在行为表的行上、`clip-setup.json` 里，还是按动作的"状态"（站、坐、走、跑、倒地）分组再连边，都还没定；和打分表怎么配合（不在图上的候选直接不参与，还是先经过一个中间动作）也没定。

## 6. 明确不在这个系统里

| | 状态 |
|---|---|
| 记忆产生指向性行为 | 现在不需要。候选全部来自眼前有什么，没有地方吐出「去找昨天那个人」。真要做，是加**第四个候选来源**，且它要能指向不在眼前的人或地方 |
| 画面外也在过日子 | 同上，整套建立在「周围有什么」上，人不在场就没有候选来源。后面再看 |
| 人对人开销是平方级 | 纯实现问题，可避免，不改变上面任何一条 |
| NPC 想什么、社会关系、情绪 | 这一轮不在讨论范围 |
| 玩家干预 NPC | 不做 |

## 附：这轮参考过的现成架构

不直接采用，只用来找自己的方案在哪崩。机制细节不要信这份文档，要用就重查原文。

- **The Sims** — 场上物件广播「用我能得到什么」，NPC 按当前需求加权后在高分里随机取一个。算法只有一个、跑在 NPC 这边，物件挂的是数据不是逻辑。**本方案的骨架来自这里**，但把产生方从「物件」扩到「物件 + 人 + 自身」，因为街景上物件不是最多的那类
- **RimWorld** — ThinkTree 固定优先级依次问 JobGiver，第一个有效的就用。加一个行为要同时动 JobGiver + JobDriver + ThinkTree 里的位置，撞「加行为便宜」，**未采用**
- **GOAP** — 动作写前置条件和效果，规划器从目标倒推。加动作要跟已有动作的前后条件咬合，撞「改旧东西不牵动全身」，**未采用**
- **Ready or Not** — 逐帧评分取最高，后来补了 Gates（动作先要有资格才参与打分）。**本方案的资格条件来自这里**
- **Dragon Age: Inquisition** — 角色越界时让「返回区域」的分高过所有战斗行为，靠的还是同一次比较。说明「必须坚持到某条件满足」不需要另设机制
- **Hamsterdam / ALIVE** — 唯一真做过「越做越容易换」的（疲劳值，分数乘以 1 减疲劳），但同时配了行为间相互抑制。作者自己报告：抑制弱了角色反复横跳，抑制强了抓不住新机会
- **Versu / ABL** — 双人互动做成共享实例或接洽协议。本方案在有物件记账时不需要它，**只有身体接触类保留了请求形式**
